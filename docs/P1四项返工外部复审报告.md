### 剩余 P2：IPC 发送错误会跳过终止及等待

- **定位：** `scripts/client-server-fixture-lifecycle.mjs:52–64`；`scripts/client-server-check.mjs:108–110`。相关缺失断言位于 `scripts/test/client-server-fixture-lifecycle.test.mjs:44–77`。
- **触发条件：** 子进程仍在运行时，`child.send('shutdown')` 同步抛错，或 IPC 发送等错误触发 `child` 的 `error` 事件，使 `context.exited` 拒绝。
- **控制流：** send、等待和 `kill()` 位于同一个 try。上述任一异常直接进入 catch，跳过后面的有界等待和终止。`context.exited` 把 error 与真正 exit 合在一个 Promise 中，也不能用已经拒绝的 Promise 确认后续真实退出。
- **影响：** 函数报错、下一桌不会启动，故没有证明会超两桌；但合成 HTTP 服务可能仍活着、持有端口和写者租约，不能宣称失败资源已经清理。没有运行复现或检查实际遗留进程，不声称本机已发生该泄漏。
- **兜底核查：** 联调脚本没有外层进程清理钩子；`signal-fixture.mjs` 仅收到 shutdown 消息后触发 SIGTERM；服务 main 的 exit 钩子只在进程已退出时释放租约，不促使活进程退出，也没有 IPC disconnect 自动关闭逻辑。不能假定父进程退出会完成此收尾。

Node 官方文档说明，发送消息失败可以产生子进程 error，而 error 不保证随后发生 exit；因此 error 不能充当退出证明。[Node ChildProcess 事件说明](https://github.com/nodejs/node/blob/main/doc/api/child_process.md#event-error)。本缺陷判断来自项目的具体控制流，官方说明只用于确认事件语义。

**最小修补及离线验收：**

1. 独立收集 IPC／error 错误；无论发送是否成功，都继续按有界收尾流程等待，必要时尝试终止。保留原始错误，不能将它吞掉后报告成功。
2. 将实际 exit／close 证明与 error 通知分开；不要反复等待一个已经拒绝的 Promise。终止未确认或租约仍在时继续报告失败并保留目录，不伪造释放。
3. 增加两个无服务的假子进程用例：send 同步抛错但进程仍活；error 发生但没有 exit。均断言仍尝试终止、等待独立退出信号、检查租约、保留原错误，且不创建下一桌。另断言 kill 后仍无 exit 会有界失败。

无需真实模型、HTTP 联调或全量矩阵。该发现继续使用原 `P1-AUDIT-TABLE-LIMIT` 编号，不新建重复活动项。
