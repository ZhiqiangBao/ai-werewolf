# AUDIO-LIFECYCLE 评估

评估日期：2026-11-03。结论：本项评估完成，实时音频仍有明确的失败恢复和取消边界；测量不构成修复或流式播放能力。建议后续处理播放失败丢队列，并定义客户端断开时共享合成任务的产品语义；逐席音色暂不作为必做功能。实际问题的稳定编号及验收条件由项目唯一待办入口维护。

## 范围与方法

只使用项目默认 Qwen Token Plan 和固定合成文本，未接触真实房间或用户浏览器。`packages/session/scripts/audio-lifecycle-measure.ts` 通过现有 `speechProvider`、`SpeechService` 和 `synthesizeQwen` 执行，每条使用全新隔离目录做冷缓存，再原文热读一次；临时禁用显式视频缓存目录，退出时恢复环境与 `fetch`。探针在本进程中观察响应流，不记录请求正文、凭据、签名地址、音频和请求 ID。真实媒体与原始元数据留在忽略的数据目录；随报告保存的 [脱敏数据](AUDIO-LIFECYCLE数据.json) 仅含长度、时间、字节数和结果。

分两轮：第一轮发现“首个媒体传输字节”可能只是 WAV 文件头，不能代表实际音频数据；第二轮增加 RIFF 块解析，记录 WAV `data` 块的首字节。每轮两段短文本（11、13 个 Unicode 字符，含标点）、两段长文本（各 78 字符）；每段各一次冷缓存和热缓存。两轮共 8 次实际合成 POST 和 8 次媒体下载，8 次冷缓存成功，8 次热缓存均不发网络请求。另有受限环境中 4 次 DNS 解析失败，均未建立上游连接；随后使用已授权的网络权限在同一服务重试。没有测量费用，也无法根据断开行为断言上游是否计费。

测量环境为 Windows `10.0.26300`、x64、Node.js `v24.18.1`；模型 `qwen-audio-3.0-tts-plus`，固定音色 `qwen-audio-3.0-tts-plus-longshuojizhu`，速率 `1.08`，WAV 采样率 `24000 Hz`。默认指令要求普通话自然清楚朗读原文、准确读出玩家号码、不添加或改写；指令 UTF-8 SHA-256 为 `d297de130ccaf6d7d785f8dc5b64fa0e6a5b77b1fcd4cf117cde2e506b6cf9df`。第二轮实际测量脚本的 SHA-256 为 `c945897c13e040c6f5766741002d6312273d9c1d531ff5d0b9bbb65f459eea1c`；当前脚本的 SHA-256 为 `3f3695d2dd5d7f5fab88533f093ad3d03570b9f9c5aee9d3967e723f3f576876`，仅在第二轮脚本基础上增加 `--live` 显式开关，观测逻辑相同，未因此重测。第一轮脚本尚未加入 WAV data 首字节探针。

从项目根目录复现当前测量（依赖已安装，并具备已授权的项目 Qwen Token Plan 凭据和网络访问）：

```powershell
.\node_modules\.bin\tsx.cmd packages/session/scripts/audio-lifecycle-measure.ts --live
```

每次执行会发送四次真实合成请求并生成四次热缓存读取；不带 `--live` 时脚本直接退出，不调用服务。

时间均为从本地调用 `SpeechService.render` 起的毫秒数：

- 首个文件字节可能仅是容器头；`data` 首字节是识别出的音频样本数据，仍不表示浏览器解码、设备输出或人耳可听。
- 上游完成是本次响应流消费结束；此次均先收到合成响应再下载媒体，因此该时间是媒体下载完成，不是 URL 出现时刻。
- 服务就绪包含完整音频校验和缓存写入，**不是**网页 `play()`、`onplaying` 或真实扬声器起声。当前 HTTP 等待完整服务结果才发响应，网页还须等待完整 blob，再触发 `ready` 和 `play()`；`ready` 本身早于 `play()`，不等于播放开始。这里没有运行真实浏览器或测量网络往返、排队、解码、自动播放限制及扬声器延迟。

## 生命周期和权限核对

- **失败后的队列：** `SpeechPlayback.tsx` 在新投影同步时先将事件记入 `SpeechCursor.seen` 并加入队列；播放失败时清空队列和当前条目、关闭自动朗读。此后重新同步相同投影不会再次入队，重新开启只会选择当前最新一条，因此中间尚未播放的条目可能丢失。`apps/web/test/speech.test.ts` 检查游标去重，`speech-output.test.ts` 检查输出驱动；本次未运行 React hook 的端到端测试，以上队列结论来自源码路径核对，不能将底层测试当作 hook 行为实测。
- **中止：** 浏览器驱动停止时会中止 HTTP 请求；服务端 `speech.render` 接口没有接收该请求的取消信号，合成仅受内部 240 秒超时约束。当前约定下页面停止或 HTTP 断开不保证撤销上游合成。独立本地 HTTP 实例和可控假提供方测试证实客户端断开后信号未取消、合成继续并可写缓存。该实验不能证明真实提供方何时计费，亦不能保证取消费用。是否改变这一行为是待定义的产品语义，并非要求中止所有共享请求。
- **并发和缓存：** 本地假提供方测试验证同文合并、同时最多两个不同合成、失败释放槽位并启动等待任务，成功后同文命中缓存。它不等同于真实上游并发和计费测试。
- **音色与权限：** 实时服务端音色属于来源配置，浏览器原生音色属于页面选择；发言请求只提交事件号和来源标识，没有逐席音色字段。视频记录中的 `seat-N` 是制作映射，不等同实时配置。`RoomViewService.speechText` 从凭证对应投影取已提交发言；现有 `human.test.ts` 验证公开发言、不同凭证的私密投影和非法编号边界。若以后实现逐席音色，应继续按授权投影取事件、避免暴露身份或私人内容，并明确来源、座位和缓存键的关系。
- **行动时限：** 房间运行时维护后端 deadline；当前音频播放、暂停和下载没有与之联动。不能宣称朗读等待不挤占真人决策时间。

## 验证与建议

相关语音、HTTP 中止、缓存并发和真人视角权限共 6 个测试文件、26 项测试通过；`tsc -p tsconfig.json --noEmit` 通过。网络受限环境中的本地临时目录重命名报 `EPERM`，使用权限允许的本机测试环境重跑通过；真实测量的首次 DNS 失败如上单独记录。没有实际网页或扬声器播放测试。

建议将“播放失败保留或可恢复待播事件”和“定义客户端取消及共享合成任务的行为”分别纳入后续工作；后者须先明确引用计数、多个请求共享任务、无订阅者时是否取消及并发槽位等语义，再决定是否实施取消和测试。逐席音色目前为可选体验需求；如将来选择实施，应先设计权限、默认值、缓存及旧房间兼容。音频和行动时限的关系需在产品方案中明确，不以本次延迟数据替代真人体验验证。
