# 国际化扩展指南

本指南面向维护项目的开发者和本机操作者，说明如何保持个人界面语言与房间对局语言分开，并扩展中、英、日资源。不要把已有对局或玩家原话当作待翻译的模板。

## 两种语言各自负责什么

| 语言 | 保存位置与作用 | 资源入口 |
| --- | --- | --- |
| 界面语言 | 每位用户在当前浏览器单独保存；控制按钮、表单、菜单和辅助提示。 | `apps/web/src/i18n.tsx`、`apps/web/src/locales/ui.ts`、`apps/web/src/locales/game-ui.ts` |
| 对局语言 | 房间配置的一部分；开局前选择，开局后固定。控制规则卡、法官消息、系统事件、工具说明和模型收到的语言要求。 | `packages/protocol/src/locale.ts`、`packages/protocol/src/locales/` |

切换界面语言不会改变房间设置。玩家发言、玩家自定义文字和昵称不自动翻译。缺少语言字段的旧房间按 `zh-CN` 处理；无法从保存数据可靠重建的历史文字保留原值，不通过翻译或重新结算来生成新历史。模型会收到使用对局语言的要求，但模型输出语言不作保证。

视频导出只保持现有 `video-locale`／`VIDEO_LOCALE` 接口兼容。它不意味着视频字幕、配音和历史正文也纳入本轮三语完整本地化。

## 注册英语变体或方言

语言标识使用规范 BCP 47 标签。`en-GB` 不是仅靠标签就能启用的选项：必须注册界面包和对局包，并在浏览器构建与服务端进程中加载相应资源。新包可回退到已注册的英语包，只覆盖确实不同的字符串。

在 `packages/protocol/src/locale.ts` 的内置语言包之后注册对局语言。这里的注册表由浏览器构建与服务端共用：

```ts
registerGameLanguage({
  id: 'en-GB',
  label: 'English (UK)',
  languageName: 'British English',
  speechLang: 'en-GB',
  ttsLanguageHints: ['en'],
  fallback: 'en',
  messages: {
    '狼人阵营': 'Wolf team',
  },
});

const gameCoverage = checkGameLanguage('en-GB');
```

在 `apps/web/src/i18n.tsx` 的内置界面语言包之后注册同一标签：

```ts
registerUiLanguage({
  id: 'en-GB',
  label: 'English (UK)',
  fallback: 'en',
  messages: {
    '界面语言': 'Display language',
  },
});

const uiCoverage = checkUiLanguage('en-GB');
```

以上示例只覆盖少数地区差异；其余内容由 `en` 回退提供。实际界面或对局开始前，应让检查结果中的 `missing` 为空；`inherited` 表示有意沿用回退语言。只有完成注册、资源检查和两端部署后，新标签才会出现在选择列表并能被服务端接受。

## 维护三语目录

协议消息分成通用游戏文本、补充游戏文本、页面呈现文本、动态目录文本和服务错误。`packages/protocol/src/locales/catalog.ts` 的 `catalogMessages` 补充版型名称与描述、角色阵营／类别／摘要、规则选项和风格目录中缺少的翻译；`packages/protocol/src/locales/service.ts` 补充协议及服务端已知错误。新增前应先用 `engineCatalog()` 和房间 `catalog()` 核实真实导出值，再与 `messages.ts`、`game-additions.ts`、`presentation.ts`、`catalog.ts` 的已有源模板核对。新增资源后，还要把对应导出并入 `locale.ts` 的 `checkedMessages` 输入，注册表才会加载这些译文。

错误资源只收录项目生成的稳定模板，例如 `LocalizedError.localization.key`、`ApiFailure.localization.key`、错误码默认文案和已知配置错误。不要拆分或猜译供应商的动态响应、模型名称、接口地址或密钥。供应商校验的原始错误如果当前不会直接呈现，就保留通用、可执行的本地提示，不要编造供应商原文的翻译。

网页资源放在 `ui.ts` 与 `game-ui.ts`。游戏和网页的检查器会报告缺项与回退项；`checkedMessages` 和 `checkedUiMessages` 会拒绝重复源模板、空译文或占位符不一致。三语模板中的 `{0}` 等编号必须一致，且每个源模板只能定义一次。不能用 `Object.fromEntries` 的覆盖行为掩盖重复键，也不要用本地化显示文字代替角色 ID、规则选项 ID、工具名、参数名或枚举值。

扩展或修改资源后，在仓库根目录运行：

```bash
pnpm exec tsx scripts/check-locales.ts
pnpm typecheck
pnpm build
```

语言检查会核对简体中文、英语和日语的资源缺项、占位符与重复模板。若 `missing` 不为空，先补译文或明确注册回退；若是有意继承，应确认回退确实代表目标语言，并记录其为有意选择。构建网页后，在新房间中分别检查界面选择器和对局语言选择器；不要用改写旧记录来验证。

## 在浏览器和服务端保持一致

这些注册表是各自 JavaScript 进程内的资源，不会因为浏览器切换语言而自动添加到 Node 服务。对局包位于共享 `@werewolf/protocol` 路径，需同时进入网页构建和服务端依赖；网页包只进入 `apps/web`。开发模式下重启服务以重载服务端模块；生产部署时，更新代码后重新构建网页并重启服务。只在浏览器注册一个房间语言，服务端仍会拒绝未注册标签；只在服务端注册，网页也不会列出该选项。

所有资源应在调用 `registerGameLanguage`／`registerUiLanguage` 的进程启动阶段加载，然后运行覆盖检查。不要在单个请求处理器里临时注册语言，也不要根据用户的界面语言改写房间的 `locale`。房间 locale 在游戏开始后固定，界面 locale 仍属于各自浏览器。
