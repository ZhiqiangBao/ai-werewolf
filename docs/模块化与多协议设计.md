# 模块化、版型扩展与多协议设计

检查日期：2026-10-31。本轮已实现思考强度按钮；本文中新增版型、能力层和 Responses / Anthropic 适配器均为后续设计，尚未实现。

## 当前模块化情况

现有分层清楚：`engine` 负责规则与事件，`session` 负责座位上下文与调度，`llm` 负责模型调用，`protocol` 提供共享类型，网页从目录和座位投影渲染。规则引擎不依赖网络或模型。

角色通过 `registry.ts` 注册。`RoleModule` 已有初始化、私密身份附录、规则卡、夜间顺序、决策步骤、中断、死亡技能和结算修正等扩展点。已有身份重新组合成版型比较容易；动态模仿技能和多种 API 协议还没有完全模块化。

当前有三个具体缺口：

- `packages/engine/src/catalog.ts` 的固定技能工具仍由 `roleTools()` 的身份分支提供。只注册一个新角色，AI 不会自动得到它的固定技能工具。
- `Ctx.roleOf()` 按 `player.role` 取角色模块，角色身份、查验表现、狼队互认与能力还没有充分分离。原有技能也经常通过 `seatsOf('witch')` 等查找使用者，复制技能不能只复用函数名称。
- `packages/session/src/agent.ts` 将 `ChatMessage[]` 当作持久化的座位历史，`ChatMessage` 本身就是 Chat Completions 的消息格式。已有适配器接口，但上下文仍与这一种协议耦合。

因此，我的判断是：基础分层合理，适合继续演进；对复杂新角色和多协议，应该先补这几个接口，避免继续增加集中分支。

## 增加十二人镜隐迷踪，需要改哪些文件

如果只调整已有身份的人数和组合，主要改 `packages/engine/src/presets.ts`，并增加人数、角色限制和模拟对局测试。不要覆盖旧 `standard12` 的含义，应增加新的版型 ID，保留旧房间与复盘的规则含义。

镜隐迷踪需要两个新角色。官方介绍的配置是三名普通狼人、一名觉醒隐狼、四名平民，以及魔镜少女、女巫、猎人、守卫；魔镜少女查具体身份且不能重复查验，觉醒隐狼涉及模仿与延迟获得技能。[官方版型与角色介绍](https://langrensha.com/news/official/20231113/26904_1119726.html)

下面是按当前代码定位的改动范围，新增文件名为建议命名：

| 文件 | 所需工作 |
| --- | --- |
| `packages/engine/src/roles/mirror-maiden.ts`（新增） | 具体身份查验、查验记录、重复目标校验、私密结果与身份说明。 |
| `packages/engine/src/roles/awakened-hidden-wolf.ts`（新增） | 模仿选择、获得技能的时点、刀权继承、私有资源与对应决策。 |
| `packages/engine/src/builtin.ts` | 导入并注册两个角色。 |
| `packages/engine/src/presets.ts` | 增加独立版型 ID、人数配置和规则覆盖。 |
| `packages/engine/src/types.ts`、`context.ts` | 增加技能实例与查验身份等扩展点，区分真实角色、阵营、可见身份、获得的能力和刀权。 |
| `packages/engine/src/catalog.ts` | 接入新角色固定工具；建议将角色工具定义下放到 `RoleModule`，通用工具继续集中复用。 |
| `packages/engine/src/roles/werewolf.ts` | 按规则处理普通狼与隐狼的互认、密谈、带刀资格和继承。 |
| `packages/engine/src/roles/{witch,guard,hunter}.ts` | 将需要被复制的技能提取为可复用能力，原身份模块负责装配。 |
| `packages/engine/src/flow/night.ts`、`deaths.ts` | 接入技能启用时点、攻击与保护来源、复制后的死亡技能；已有结算钩子能覆盖的部分不必重写公共流程。 |
| `packages/session/src/agent.ts`、`packages/llm/src/mock.ts` | 补充新工具的行动提示和模拟玩家策略；通用回退只能保证参数合法，不能证明新规则正确。 |
| `packages/engine/test/`、`packages/session/test/` | 覆盖查验表现、模仿各身份、启用时点、狼队信息隔离、刀权继承、死亡连锁、存档恢复与完整对局。 |

规则卡与网页角色名称大多来自角色目录和投影，通常不用为每个新角色增加页面分支。`rulecard.ts`、`flow/win.ts`、`flow/sheriff.ts`、投影与协议类型需要按规则差异检查；只有新字段或判定确实需要时才修改。

不能把隐狼的 `player.role` 直接改成被模仿者。否则会同时改变它的胜负阵营、屠边统计和可能的私密信息权限。建议保留真实角色与阵营，另外存储 `appearance`、`abilities`、`activeFromNight` 和独立的刀权状态。查验经统一函数计算结果，而不是直接读取底牌；具体对哪个观察者呈现什么身份，由所选规则版本决定。

为保持每个座位整局工具 Schema 稳定，隐狼开局就获得本版型所有潜在技能的固定工具定义。获得哪个技能、何时可用、药品是否耗尽，均由引擎校验，并通过追加私密事件告知本人。不会因模仿结果改写系统提示、工具顺序，也不会将结果通知目标或其他座位。

实际实现前需要固定一份完整规则卡，尤其是模仿的具体效果、技能启用、继承刀权、死亡技能以及警徽相关细则。官方介绍没有覆盖所有边界，不能仅根据版型名称推断完整判定。

## 当前模型接口

目前真实模型调用只实现了 OpenAI 兼容的 Chat Completions：

- `packages/protocol/src/index.ts` 的 `AdapterKind` 只有 `mock` 和 `openai_compatible`。
- `packages/llm/src/index.ts` 只在模拟玩家与现有适配器之间分派。
- `packages/llm/src/openai.ts` 的 `chatUrl()` 构造 `/chat/completions`，请求和回复都按 `messages`、`tool_calls` 处理。
- `packages/session/src/qwen-presets.ts` 的地址规范化与配置导入也以此为基础。

`toolMode='json'` 只是同一接口上用 JSON 表达行动，不是 Responses 协议。把地址换成 `/responses` 或 `/messages` 不足以接入新协议。

## 建议的协议选项与实现边界

在模型条目上增加 `apiProtocol`：`chat_completions`、`responses`、`anthropic_messages`；旧条目缺省仍为 `chat_completions`。座位选中模型时继承协议，自定义地址也能明确选择。模拟玩家与远程调用仍作为控制方式，不用三个协议混淆角色或游戏规则。

服务端按协议选择适配器，将模型能力、认证头、URL 规则、流式事件、工具结果和思考参数分别转换。界面显示“Chat Completions / Responses / Anthropic Messages”，测通也使用所选协议。失败时保留明确错误，不悄悄切换协议重新发送整段历史。

| 文件或目录 | 后续调整 |
| --- | --- |
| `packages/protocol/src/index.ts` | 配置协议枚举与能力视图，旧字段兼容。 |
| `packages/session/src/model-library.ts`、`qwen-presets.ts` | 保存/导入协议，按协议规范化地址与模型条目标识。 |
| `packages/session/src/manager.ts` | 固定调用绑定、按协议分派，保留现有行动许可、时限和引擎校验。 |
| `packages/session/src/agent.ts`、`store.ts` | 引入带版本的座位语义历史和协议续接状态；旧 `messages` 可读取迁移，不重新执行历史工具。 |
| `packages/llm/src/types.ts`、`prompt.ts`、`index.ts` | 将公共请求结果从 Chat 消息类型解耦，继续共用规则提示与 ToolSpec。 |
| `packages/llm/src/transcript.ts`（新增） | 定义文本、助手回复、工具调用和工具结果的公共结构及业务调用编号。 |
| `packages/llm/src/adapters/{chat-completions,responses,anthropic}.ts`（新增） | 各自的编码、解析、原生状态保存与流式归一化。 |
| `packages/llm/src/transport.ts`（新增） | 共用总超时、取消、受控重试和错误脱敏；协议特有降级由各适配器处理。 |
| `apps/server/src/`、`apps/web/src/pages/Setup.tsx` | 配置接口、模型管理和测通入口支持协议选项。 |

这轮新增的思考档位可以保留为公共偏好，实际能力和参数映射以后交给各协议适配器。不能把当前 Chat Completions 的思考参数原样用于 Responses 或 Anthropic。

## 座位 Agent 的上下文如何处理

保留三层数据：房间事实日志、每个座位自己的语义历史、该座位的协议续接状态。

房间事件决定谁有权知道什么。座位语义历史只含已向它送达的事实、该座位自己的助手回复、工具调用与对应回执。其他玩家的发言仍带座位标签，作为外部发言送达，不能被转换成这个座位自己的助手回答。上帝日志或其他座位历史不能直接拿来拼上下文。

协议状态属于同一座位的同一模型绑定，包括 endpoint、model、protocol、凭证版本及本地 generation。十二个座位分别保存，哪怕用了同一个 API Key，也不能共用一个 `previous_response_id` 或服务端 conversation。

同一次“投票 → 工具反馈”的转换如下：

| 协议 | 助手输出 | 下一次输入的反馈 |
| --- | --- | --- |
| Chat Completions | `assistant.tool_calls` | `role: tool`，关联 `tool_call_id`。 |
| Responses | `function_call` output item | `function_call_output` input item，关联 `call_id`。 |
| Anthropic Messages | assistant 内容中的 `tool_use` | user 内容中的 `tool_result`，关联 `tool_use_id`。 |

Responses 的状态既能由本地回传 items 管理，也能用 `previous_response_id` 串联；使用后者仍需每次发送稳定的 instructions。建议第一版采用本地完整历史，便于重启、检查、切换与重放，再把服务端串联作为可选优化。[OpenAI 迁移说明](https://developers.openai.com/api/docs/guides/migrate-to-responses?api-mode=responses)

本地管理 Responses 上下文时，需要保留完整原生 output items，包括协议返回的 reasoning 和 phase 等信息；不能只摘取 `output_text`。续接 ID 也不意味着历史输入不再计费。[OpenAI 会话状态文档](https://developers.openai.com/api/docs/guides/conversation-state)

Anthropic 的工具回执必须紧接对应工具调用；同一个 user 内容数组中，工具结果放在新增文本之前。新法官消息到达时，先补齐上一轮工具回执，再追加新消息，避免工具链断裂。[Anthropic 工具调用格式](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)

有些协议还需要回传不可改写的原生思考块或签名。它们应单独保存在该座位的私有协议状态中，按供应商规则原样续接；不会转成公开发言，也不会塞进另一个座位的消息。Anthropic 的 thinking block 和 signature 就有这种要求。[Anthropic 思考文档](https://platform.claude.com/docs/en/build-with-claude/thinking)

因此，“思考只供显示”不能成为所有未来协议的一条通用序列化规则：展示摘要与协议要求的续接数据要分开处理。前者不会成为法官事实，后者也不应被当成普通文本跨模型复制。

换模型或换协议时，保留座位有权看到的语义历史，清除不兼容的原生续接链；适配器重新编码文本与工具往返，不能执行第二遍历史行动。旧供应商的加密思考、签名和缓存状态不可移植，不承诺保留其内部推理状态。第一版继续限定开局前配置；若以后允许对局中切换，先取消旧请求并递增 generation，拒绝迟到的旧回复。

初期保持完整座位历史，不默认摘要或截断。以后遇到上下文窗口限制时，需要按座位独立处理，并完整保留未结束的工具调用与结果、行动许可和私密规则状态，不能从上帝视角生成摘要。

## 建议实施顺序与验收

先补角色固定工具和可复用能力的扩展点，再实现镜隐迷踪两个角色；模型接口先完成语义历史与旧存档兼容，再分别接入 Responses、Anthropic。这两个方向可以独立推进，游戏规则不应依赖所选 API。

多协议验收至少覆盖：同一座位旁听与行动隔离、一次错误工具调用的修正、多工具错误回执、流式中断与剩余时限、重启续接、协议切换不重复行动，以及三个协议下都不会泄露其他座位信息。对局推进仍由同一规则引擎判定。
