# 如何写上帝解说

本节给 AI agent 和真人制作者同样的写作方法。`narration.json` 的自动内容是起稿模板，程序没有代替制作者读懂整局、选择看点和润色。完成下列工作后再开始正式配音。

## 读什么、产出什么

运行 `video:make --room=ROOM_ID --prepare-only` 后，从本局 `plan.json` 找到 `editorialContextFile`、`narrationFile` 和 `voiceFile`。默认位于 `data/video/ROOM_ID/`；指定独立制作目录时以实际路径为准。

先读 `editorial-context.json` 的 `cast`、`ruleCard` 和 `facts`，梳理本局实际转折。`playerSpeechIndex.opening` 只是发言开头，判断一位玩家说了什么时必须再读 `data/exports/ROOM_ID-video-script.json` 中相同 `sourceSeq` 的完整条目。真人操作也只需阅读这些 JSON，无需调用专属 agent 工具。

最终产物是编辑好的 `narration.json`：保留本局 `roomId`，对允许修改的非玩家条目设置 `edits`，完成事实核对后记录 `review`。无需改原始房间、玩家原话或事实事件。

## 先做锚点表，再写句子

1. 按时间顺序列出关键事件。优先找投票与真实身份的反差、狼队计划和实际行动的差别、关键药物与守护效果、警徽变化和残局人数变化。
2. 为每个候选点写四项：`sourceSeq`、此时已发生的事实、观众容易漏掉的关系、准备补充的一句话。用不到的节点删去，不必每条事件都点评。
3. 核对该锚点以前的记录。上帝可点出真实身份和已发生的夜间行动；后续谁被刀、谁被毒、谁获胜，留到相应事实出现以后再讲。
4. 引用发言须读完整原文。可以说“他这段话把矛头指向女巫”，但不能把玩家口头声称的查验写成引擎确认的查验，也不能替玩家补充没说过的理由。

例如，**以下为虚构教学材料**：本局身份表确认 2 号是预言家；`sourceSeq=20` 是投票结果，2 号六票被放逐。此时可以补“六票把真预言家送走了。这一轮的站边和票型，值得回头一起看。”不能写“女巫今晚会毒中狼人”，因为那是之后尚未发生的行动。

## 分别写开场、过程和收尾

| 部分 | 写作顺序 | 需要避免的内容 |
| --- | --- | --- |
| 开场 | 交代板型与上帝视角 → 用本桌人物或对局特点带入 → 接首夜 | 提前报赢家；复述整张规则卡；编造玩家台词 |
| 过程点评 | 点出已发生的事实 → 解释与真实身份或前文的反差 → 必要时提醒关注票型或发言 | 重念法官结果；把计划当结果；未记录的心理、动机；未来行动剧透 |
| 终局收尾 | 核对胜负 → 选两三个关键转折串起因果 → 点出本局最值得回看的表现 | 逐条朗读整份复盘；只堆“精彩博弈”等空话；混用其他房间事实 |

过程点评通常一两句就够，用自然口语写具体的人、事和反差。先写简短稿，配音后以实际时长检查节奏；不要插在同一玩家连续发言的分段之间。轻松吐槽可以有，语气依据实际发言，不能把推测写成事实。

## 怎样填进 narration.json

`edits` 的键是原始非玩家条目的 `sourceSeq`，不是视频秒数或发言座位。开场 `game.start` 和终局 `review` 可用 `text` 替换，并设置 `voiceKey: "commentator"`；投票、警徽等法官结果保留，在 `after` 中追加点评。每次编辑都写 `reason`，指出依据。

沿用上面的**虚构教学材料**，仅演示一条结果后的追加格式：

```json
{
  "20": {
    "reason": "保留法官投票结果",
    "after": [
      {
        "text": "六票把真预言家送走了。这一轮的站边和票型，值得回头一起看。",
        "reason": "序号20确认2号六票被放逐；本局身份表确认2号为预言家"
      }
    ]
  }
}
```

把实际的条目合并进本局已有 `edits`，不要把示例的 20 当成自己房间的锚点。完整格式与原法官模板处理见 [准备材料中的编辑格式](preproduction.md#写回准确的编辑格式)。

## 可交给任意文本模型的写作任务

真人可以按上述方法直接编写，也可以把以下任务与材料交给任意可用的文本模型，再逐句审核。AI agent 同样可自行完成，无需另开模型接口。

```text
请为这局已结束的狼人杀制作上帝解说。
材料：本局 plan.json、editorial-context.json、narration.json；
需要引用的玩家发言附上原始剪辑稿中对应 sourceSeq 的完整条目。

先列出“锚点 sourceSeq → 当时已发生的事实 → 观众需要理解的关系 → 点评”表。
再润色开场、选出的关键点评和终局收尾，合并进 narration.json。
保持本局 roomId、玩家原话、身份、行动、票型与胜负不变。
过程点评只依据锚点及以前的事实；全局复盘只能用于终局收尾与事后核对。
玩家声称、计划、实际执行和结算效果要分清，不编造动机或未来行动。
结果后的点评用 after，保留法官原结果；开场和收尾用 commentator。
每条写具体 reason。语言自然、简短、有本局的具体看点。
先输出可核对的依据与编辑稿；实际核对完成后才填写 review，不提前声明已审核。
```

## 核对后才能交给自动化

逐句核对人物、身份、目标、票数、行动效果与时间位置；确认玩家原话没被改动、法官结果没被点评覆盖、过程没有使用未来结果。核对完才在 `narration.json` 写入：

```json
"review": {
  "status": "reviewed",
  "method": "human-editor",
  "factsChecked": true,
  "playerQuotesUntouched": true,
  "futureResultsNotUsedInProcessCommentary": true,
  "notes": "填写实际核对范围及仍需留意的地方"
}
```

`method` 按实际执行者填 `human-editor` 或 `model-editor`。这是已完成编辑审核的记录；AI agent 可以自行核对，不需要为此增加一轮用户审批。

然后运行 `pnpm video:make --room=ROOM_ID --check-only --encoder=cpu`，查看本局 `output/materials-check.json`。它会检查本局对应关系、锚点、玩家原话、音色参数和审核记录，不调用 TTS。通过表示结构和准备记录满足启动要求；解说的事实语义与表达质量仍由上述实际阅读审核保证。
